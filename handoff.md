## 1. What this project is

A casual, ad-funded Android endless runner built in **Godot 4.x / GDScript 2.0**: a chaotic shih tzu chases a sentient vacuum cleaner to get its stolen treats back, hopping over obstacles and deflecting flying household objects with timed bark blasts, then CHOMPing the vacuum during a "Zoomies" burst.

Full specs live in three companion docs in this repo — read them in this order:
1. `bark_and_chomp_project_plan.md` — phased build plan, milestones, gates, timeline, risks.
2. `game_design_document.md` — mechanics, characters, economy, monetization, feel.
3. `technical_design_document.md` — Godot project structure, scripts, node layout, build spec for coding agents.

**Locked guiding principles** (do not relitigate these without the user):
- One dog, forever. Depth via costumes, not new characters/breeds.
- The vacuum wants to *clean* the treats, not hurt the dog — all its behavior flows from that.
- Two inputs only: tap = hop, hold = bark. All skill expression is timing.
- Runs are short (60–120s); nothing from the backlog gets built until the core loop is proven fun on a real phone.
- Every design question answerable by playtesting gets playtested, not debated.

**Milestone 1.1 on-device debugging journey (this is the real story — earlier drafts of this doc claimed first-try success, which was wrong):**
1. First playtest: hop did not respond to tap at all. Root cause: `player.gd`'s `_physics_process` unconditionally zeroed `velocity.y` whenever `is_on_floor()` was true — but `is_on_floor()` is a cached value only refreshed by `move_and_slide()`, so the physics frame right after a hop request would still see stale "grounded" state and wipe out the just-applied jump velocity before it took effect. **Fix**: only zero `velocity.y` when on floor AND `velocity.y >= 0.0` (don't clobber an active jump). This is the current code in `player.gd`.
2. Second playtest: hop worked once, then the capsule got permanently stuck against the red obstacle and stopped responding to taps entirely. Root cause: `hop_impulse=9.0` (TDD §3 default) only gives ~93px of rise, but the placeholder obstacle is 96px tall — the capsule hit the obstacle's *side* wall mid-air instead of clearing it, got pinned there, and since wall contact ≠ floor contact, `is_on_floor()` never became true again, permanently blocking all future hops via the `_on_hop_requested()` guard. **Fix**: added `hop_impulse = 12.0` override in `resources/tuning.tres` (apex ≈164px, ~1.7x the obstacle height for margin). Correct fix location per TDD's tuning-as-data principle — the script default in `tuning.gd` was left untouched; only the `.tres` instance got the override.
3. Third playtest (after fix #2): capsule cleared the obstacle correctly, but tapping over the green floor area did nothing while tapping elsewhere hopped fine. Root cause: `ColorRect` extends `Control`, not just a 2D visual — the `Ground/Visual`, `Player/Visual`, and `Obstacle/Visual` placeholder ColorRects all had the default `mouse_filter = STOP`, so any touch landing within their (large) rectangles was consumed as a GUI input event before it ever reached `InputController._unhandled_input()`. The Ground ColorRect alone covered most of the lower half of the screen. **Fix**: added `mouse_filter = 2` (MOUSE_FILTER_IGNORE) to all three placeholder ColorRects in `main.tscn`, `player.tscn`, `obstacle.tscn`.
4. Fourth playtest (after fix #3): **user confirmed "yes its working"** — taps register everywhere including over the floor, hop responds reliably on repeated taps, capsule clears the obstacle. This is the first genuinely verified pass of Milestone 1.1's core mechanic.
5. Added a **Restart button** (top-right corner, screen-space `CanvasLayer`/`Button`, wired to `scripts/main.gd` → `get_tree().reload_current_scene()`) purely as a testing convenience, so retries don't require a reinstall. Confirmed working on-device.

## 2b. Milestone 1.6 — first playtest round (2026-08-19), in progress

First round of testing found a real problem, diagnosed and a fix already deployed — **re-test needed before the GO/NO-GO call.**

**Finding: bark-charge deflect timing was un-landable, even after the user explained the controls to testers.**
- Confirmed via a screen recording the user shared (analyzed by extracting frames with a locally-installed `opencv-python-headless` — no ffmpeg on this machine; this is a one-off analysis tool, not part of the project). The recording (post-explanation, ~47s) showed a tester mostly just hopping, with only **2 deliberate hold-to-charge attempts in 47s**, both landing as the intended BLAST but clearly effortful — consistent with the user's direct account: **testers understood the mechanic and still struggled to physically land the timing.**
- **Root cause, quantified from the tuning values** (`rival_target_distance=8.5`, `projectile_speed=8.0`, `run_speed=6.0`, `bark_range_units=2.5`, old `bark_hitbox_duration_s=0.15`): the runway to *start* charging is generous (~1s from throw telegraph to the projectile entering range), but the window in which release timing actually matters is only the ~0.18s the projectile spends inside `bark_range_units` before reaching the player, further gated by the 0.15s hitbox-active duration after release. That's a ~150-180ms precision requirement on the release moment judged by eye alone, with no "sweet spot" cue — a real parry-precision ask, not a discoverability problem.
- **This is a distinct finding from an earlier, now-superseded read of the same session**: the first video (before the user clarified it was post-explanation) looked like a pure onboarding/discoverability failure. It is not — the controls were explained; the timing itself is what's too tight. Don't conflate the two in future notes.
- **Fix applied** (`scripts/tuning.gd`): `bark_hitbox_duration_s` widened `0.15 → 0.3` (doubled release-timing forgiveness). Chosen as the most surgical of several tuning-only options discussed with the user (others considered: widening `bark_range_units`, slowing `projectile_speed`, adding a visual "sweet spot" cue on the projectile — deferred, try the smallest lever first).
- **Also fixed a real bug found while tracing the footage** (`scripts/player.gd`): `_flash()`'s color revert was gated on `debug_label.text == text`, so any later `_flash_label()` call (HOP/TREAT/NUDGE/CHOMP!) — which never touched color — would silently block the revert, leaving stale tint (e.g. permanent orange after a BLAST) on the player sprite. Replaced with a monotonic `_flash_id` counter so the *most recent* flash (color- or label-only) always owns reverting both text and color together. This also incidentally fixed a second latent bug: two back-to-back flashes with identical text (e.g. two "HOP"s) previously could false-positive-match on the old string comparison and revert early.
- Rebuilt and redeployed to the test device (Galaxy S24 Ultra) this session — **the build currently on the device has the 0.3s hitbox window, not what was tested in the recording above.**
- **Not yet known**: whether 0.3s is enough, too much, or needs a different lever entirely (range vs. speed vs. a visual cue). This needs a fresh re-test before deciding.

**Revised next action:** re-run testers (or at least the same tester(s) who struggled) against the current build to see if the wider hitbox window makes the deflect landable. Only proceed to the full silent-observation 3-5 person protocol below once the timing itself feels fair — no point running the full protocol against a mechanic that's still known to be un-landable.

### Round 2 (same session, 2026-08-19): two more bugs found and fixed after re-test

User reported the 0.3s hitbox window felt "much better," but surfaced two new problems. Both were real code bugs, not further tuning — found by reading the actual state machine, not guessing:

1. **"Sometimes when we press the screen and/or press and hold it does not respond."** Root cause (`scripts/input_controller.gd`): `_on_touch_down()` only accepted a new touch when `_state == State.IDLE`. Every bark release — even a whimper — enters `State.COOLDOWN` for `bark_cooldown_s` (0.85s), and during that whole window **all input was ignored, including hop taps**. The cooldown was meant to throttle re-barking (per GDD §5.1: "After blast → Cooldown 0.7-1.0s"), not block the basic hop, which per input-integrity requirements should always be reliably available. **Fix**: `_on_touch_down()` now also accepts touches during `COOLDOWN` (starts `TIMING` same as `IDLE`); the `TIMING → CHARGING` transition in `_process()` now additionally waits for `now >= _cooldown_end_ms` before allowing a new charge to start. Net effect: a quick tap during cooldown always still hops; only starting a *new bark charge* is throttled until cooldown truly ends. Minor known cosmetic side-effect: the debug label can show `IDLE`/`TIMING` instead of `COOLDOWN` for the remainder of the original cooldown window if the player taps through it — harmless, not worth tracking separately in the placeholder-debug-UI phase.
2. **"Bark should take effect till right before it touches us"** (i.e. deflect sometimes fails to register at point-blank range even when timed correctly). This is *not* a hitbox-size problem — the geometry already spans from the player's own origin out to `bark_range_units`, overlapping the player's body. Root cause (`scripts/projectile.gd`): a **signal race** between `area_entered` (deflect) and `body_entered` (hit) — both can fire the same physics frame at close range, and `_on_body_entered` only skipped registering a hit if `area_entered` had *already* run first, which isn't guaranteed. **Fix**: `_on_body_entered()` now also explicitly checks `get_overlapping_areas()` for a `bark_hitbox`-group area before registering a hit, so a genuine geometric overlap always wins over the hit regardless of Godot's internal signal dispatch order.
3. Both fixes verified with a clean headless run (`--headless --path . --quit-after 60`, zero script/scene errors), then rebuilt and redeployed to the test device. ### Round 3 (same session, 2026-08-19): point-blank deflect fix was structural, not a signal race

User re-tested round 2's fix and reported: **"still issue with Deflect not reaching point-blank range."** The round-2 `get_overlapping_areas()` guard in `projectile.gd` was a same-frame race fix — it assumed the hitbox already existed at the moment of contact, which turned out to be the wrong assumption.

- **Real root cause**: `bark_hitbox.monitorable` was only ever set `true` *after* the player released a full-charge bark (`_on_bark_released` → `_activate_bark_hitbox`). If a player tried to time their release for the last possible instant — i.e. exactly the point-blank scenario the user was testing — the projectile could physically reach the player's body in a physics frame *before* release ever happened. At that moment the hitbox didn't exist yet (`monitorable == false`), so no amount of fixing signal-dispatch order helps: there's nothing to race against yet.
- **Fix**: decoupled "hitbox is live" from "release happened." Added a new `bark_ready` signal on `input_controller.gd`, emitted once per hold the instant a charge crosses `tuning.bark_full_charge_ms` (400ms) while still held (tracked via `_full_charge_signaled`, reset on each new touch-down). `player.gd`'s new `_on_bark_ready()` sets `bark_hitbox.monitorable = true` immediately on that signal — so the hitbox goes live as soon as the charge is "full," not after release — and stays live continuously through release until `tuning.bark_hitbox_duration_s` afterward (`_activate_bark_hitbox` renamed to `_deactivate_bark_hitbox_after_grace`, now only responsible for turning it back off).
- **Net effect**: once a hold reaches full charge, the deflect hitbox protects the player for the entire remaining approach, including flush point-blank contact — landing a deflect no longer requires the release instant to beat the projectile there. The player still has to *reach* full charge (400ms) before it's live, so a late/rushed charge still produces a whimper with no protection; the skill emphasis shifts from "release at the perfect instant" to "commit to holding through the danger window," which is a small departure from the GDD §5.1 framing of release-timing as the signature skill test — worth a sentence to the user once this is confirmed to feel right, since it wasn't explicitly discussed with them before implementing (unlike round 1, where tuning-lever options were presented for a choice).
- Verified: clean headless run (`--headless --path . --quit-after 60`, exit 0, zero script/scene errors), full-file `Read` confirmation of both `input_controller.gd` and `player.gd`. Rebuilt (`--export-debug "Android"`, exit 0, only the pre-existing harmless "no project icon" warning) and redeployed to the test device (adb install -r → force-stop → monkey-launch, all succeeded).

**User immediately spotted a real design flaw in this fix, before re-testing**: "hold through the danger window is making it easy as the player can always hold to feel invulnerable." Correct — the round-3 fix as first shipped had no cap on how long the live hitbox stayed active once triggered, so continuous holding (once past 400ms) was a dominant strategy: start charging early, hold through every threat, never release until convenient. That's not a timing skill anymore, it's a toggle.

**Follow-up fix (still same session, still round 3)**: decoupled "hitbox is live" from "still being held." `player.gd::_on_bark_ready()` now starts a **fixed-length timer** (`tuning.bark_hitbox_duration_s`, still 0.3s) the instant full charge is reached, and deactivates the hitbox when that timer expires **regardless of whether the player is still holding** — guarded by a `_bark_hitbox_token` counter (same pattern as `_flash_id`) so a stale timer from an earlier hold can't clobber a newer one. `_on_bark_released()` no longer starts or extends any hitbox timer at all — release only drives the BLAST/WHIMPER visual flash now.
- **Why 0.3s specifically**: from the quantified root-cause math earlier in this section, the projectile's actual dwell time inside `bark_range_units` before contact is ~0.18s (closing speed = `projectile_speed + run_speed` = 14 u/s, since player and projectile close on each other; 2.5u / 14u/s ≈ 0.18s). A 0.3s window anchored at full-charge commit covers that 0.18s contact phase plus ~0.12s of slack for imprecise commit timing — narrow enough that holding the instant the throw telegraph starts (~1s+ before contact) will *not* still be covering the hitbox by the time the projectile arrives, so blanket "hold on any threat" no longer works; the player has to commit to full charge reasonably close to the actual contact moment.
- **Net effect**: point-blank contact is still reliably covered (the original round-3 goal — hitbox exists continuously through the danger window, no signal race), but the skill is now "time your commit to roughly overlap the incoming hit," not "release at the perfect instant" and not "hold indefinitely." Closer to the GDD's release-timing-as-skill intent than the first round-3 attempt, though the locus of precision has still shifted from release to commit-timing — worth confirming this reads as fair once re-tested.
- Re-verified: clean headless run (exit 0, zero errors), clean rebuild (exit 0), reinstalled/relaunched on the test device. **User re-tested and confirmed: "much better."** Point-blank deflect reliability and the capped commit-window (no more free-hold invulnerability) both land well. This closes out the round-3 deflect-timing thread — the deflect mechanic is now considered fair.

**Round 3 status: done.** Deflect timing (point-blank reliability + no hold-to-invulnerability exploit) is confirmed working on-device. Clear to resume the full Milestone 1.6 silent-observation playtest protocol (§3 below) — no known blocking mechanic issues remain.

### Round 5 (same session, 2026-08-19): "instant reaction to red" didn't actually work — hitbox window math bug

User report: *"when i hold when it vaccum turns red it does not bounce back — it happens only when i hold after some time of vaccum turning red."* I.e. following the hint's own instruction (hold the instant it turns red) reliably **failed** to deflect; only a *delayed* hold worked. This was a real tuning bug, not a fluke or a controls issue.

- **Root cause**: Round 3's `bark_hitbox_duration_s = 0.3s` was sized only to cover the projectile's dwell time *inside* `bark_range_units` right before contact (`2.5u / 14u/s ≈ 0.18s`, closing speed = `projectile_speed + run_speed` = 8 + 6 = 14 u/s). It never accounted for the gap between an *instant* full-charge commit and the projectile's actual arrival. Reacting the instant the red flash starts (as the hint now explicitly says to) reaches full charge at `bark_full_charge_ms = 400ms`. But total time from the red flash to contact is `throw_telegraph_s` (0.65s) + flight time to close the remaining `rival_target_distance - bark_range_units = 6.0u` at 14u/s (≈0.43s) + the 0.18s dwell ≈ **1.26s**. A window opening at 400ms and lasting only 0.3s closes at 700ms — roughly **550ms before the projectile ever arrives**. Reacting exactly as instructed closed the window early; only delaying the hold by ~550ms+ (so the window happened to land over the real contact moment) worked — exactly matching what the user observed.
- **Fix** (`scripts/tuning.gd`): `bark_hitbox_duration_s` widened `0.3 → 1.0`. Sized to cover the full ~0.86s gap between instant-full-charge (400ms) and worst-case-earliest contact (~1.2s, accounting for the rival's ±0.75u distance-noise), with margin.
- **Does not reopen the Round 3 hold-forever exploit**: the fixed-window token mechanism (`_bark_hitbox_token` in `player.gd`, paired with `_full_charge_signaled` in `input_controller.gd`) grants exactly one window per hold-*cycle*, reset only on a fresh press. Widening the window's *duration* doesn't change that it's still single-shot per commit — holding longer, or across a later throw without releasing first, still buys nothing extra.
